# DECISIONS

## ADR-1：使用 MCP WebStandardStreamableHTTPServerTransport

- 日期：2025-09
- 状态：已采纳
- 背景（遇到了什么问题）：需要选择 MCP 传输协议。可选方案包括 stdio（标准输入输出）和 HTTP Streamable。stdio 适合本地进程，但不适合远程部署和服务化场景。
- 考虑过的方案：
  - stdio transport——直接通过 stdin/stdout 通信
  - HTTP Streamable transport——通过 HTTP 端点通信
- 决策：采用 WebStandardStreamableHTTPServerTransport，挂载在 Hono HTTP 服务器的 `/mcp` 端点上。
- 为什么选这个：项目需要作为独立服务部署在内网服务器上，多个 AI 客户端通过网络访问。HTTP 模式天然支持负载均衡、健康检查、水平扩展。
- 为什么不选其他：stdio 模式只适合本地单机使用，无法支持多客户端远程访问。
- 后果：每次 MCP 请求生成新的 sessionId，服务端无状态——简化了部署但要求所有工具调用都是幂等且上下文无关的。
- 何时重新审视：当需要保持会话状态（如分页游标）时。

## ADR-2：搜索时过度查询 + 权限过滤后截断

- 日期：2025-09
- 状态：已采纳
- 背景（遇到了什么问题）：用户搜索文件时需要权限过滤，但权限 API 只能对已查询出的结果集进行过滤。如果先限制查询数量再过滤，过滤后结果可能远少于预期。
- 考虑过的方案：
  - 按用户权限构建复杂的 SQL JOIN，一次查询出有权限的结果
  - 先查询超出需求量的数据，权限过滤后再截断
  - 直接查询 limit 条，权限过滤后返回不足的数量
- 决策：搜索时查询 limit × 5 条数据，通过 `authorizeCandidateRows()` 过滤后截断至用户请求的 limit。
- 为什么选这个：权限模型在外部 API 中，无法在 SQL 层面直接 JOIN 过滤。多取 5 倍数据大幅提高最终返回足够结果的概率，且 Postgres ILIKE 查询成本可控。
- 为什么不选其他：方案 1 需要把权限模型复制到 SQL 中，维护成本极高且容易不一致；方案 3 会导致用户频繁看到不满预期的结果数。
- 后果：权限 API 调用量增加（最多 5 倍候选项），但单次调用最多 200 个 fileId，仍在合理范围。
- 何时重新审视：当 files_index 行数超过百万级，或权限 API 成为瓶颈时。

## ADR-3：文件阅读缓存优先（document_texts 表）

- 日期：2025-09
- 状态：已采纳
- 背景（遇到了什么问题）：用户频繁阅读同一文件（如热门规章制度），每次都通过 WebDAV 下载 + 解析会浪费带宽和 CPU，且 docx/xlsx/pdf 解析较慢。
- 考虑过的方案：
  - 每次实时从 WebDAV 下载并解析
  - 用 Redis 做文本缓存
  - 用 PostgreSQL document_texts 表做文本缓存
- 决策：使用 PostgreSQL 的 `document_texts` 表存储已提取的文本内容。读取时先查缓存，命中且 extract_status = "success" 则直接返回；未命中再走 WebDAV 下载 + 提取流程。
- 为什么选这个：Redis 增加运维复杂度；PostgreSQL 已在依赖中，零额外成本。文本内容通常不大（几十 KB），PG 完全胜任。
- 为什么不选其他：方案 1 浪费资源——同一份 xlsx 可能被解析几十次；方案 2 增加一个新依赖，不值得。
- 后果：需要外部同步程序在文件更新时更新 document_texts 缓存（或由同步任务一并处理）。当前读取工具不会主动写入缓存——这留给了未来的增强。
- 何时重新审视：当文本缓存写入逻辑需要内置到本服务中时。

## ADR-4：下载文件返回 base64 编码

- 日期：2025-09
- 状态：已采纳
- 背景（遇到了什么问题）：MCP 协议的工具返回值是 JSON 文本，不能直接传输二进制。需要一种方式将文件二进制内容嵌入 JSON 响应。
- 考虑过的方案：
  - base64 编码嵌入 JSON
  - 返回临时下载 URL，让客户端另行请求
  - 使用 MCP Resource 机制
- 决策：将文件 Buffer 编码为 base64 字符串，作为 JSON 字段返回。
- 为什么选这个：实现简单、无需额外的文件托管或临时 URL 管理（需要清理策略）。MCP 客户端可以直接 base64 decode 获得原文件。
- 为什么不选其他：临时 URL 需要额外的文件托管和过期管理逻辑；MCP Resource 机制增加了客户端复杂度。
- 后果：base64 编码会使传输体积膨胀约 33%，大文件会显著增大响应体积。已通过 MAX_DOWNLOAD_MB 限制（默认 50MB）来控制。
- 何时重新审视：当需要支持大于 50MB 的文件下载，或 base64 传输成为性能瓶颈时。
